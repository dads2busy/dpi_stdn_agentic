# LLM judge validation against gold standard

2026-03-31. Generated by `scripts/validate_judge_against_goldstandard.py`.

## What this is

We ran the LLM judge (the one from `scripts/judge_stage1_components_from_normalized_outputs.py`) against a human-curated gold standard of primary manufacturing components. The question: does the judge correctly tell real components from junk?

Short answer: yes. It caught every gold standard component and rejected the ones it should have. The 30 apparent "false positives" turned out to be legitimate components that the gold standard just doesn't list.

### Pipeline outputs

The pipeline ran 5 times each for v1v1v1 (single agent) and d3v1v1 (3-agent debate) using `openai:gpt-4.1-mini`. Outputs were normalized through the canonical vocabulary. We used the union of unique (technology, component) pairs across all 10 runs.

### How we measured

1. Gold standard names were normalized through the same canonical vocabulary the pipeline uses, with technology-scoped keys only (no global fallback) to avoid cross-domain mismatches.
2. Unique (technology, component) pairs were extracted from normalized pipeline outputs.
3. The judge ran on the union of gold standard and pipeline components (85 unique pairs total).
4. Metrics:
   - TP: Judge says plausible, component is in gold standard
   - FP: Judge says plausible, component is not in gold standard
   - TN: Judge says implausible, component is not in gold standard
   - FN: Judge says implausible, component is in gold standard

### What the numbers mean

Recall is 1.000 across the board -- the judge never rejected a valid component.

Raw precision looks like 0.620 because of 30 false positives. We reviewed all 30 and every one is a real component the gold standard doesn't list. So effective precision is also 1.000. The gold standard is just incomplete.

The 6 true negatives are pipeline extractions the judge correctly rejected.

## The 30 "false positives" (all legitimate)

Every one of these is a real manufacturing component. The gold standard just doesn't list them.

### Pharmaceutical Lyophilizer (7)

Air Removal System, Condensate Drainage System, Door Assembly, Pressure Vessel, Sensors and Instrumentation, Shelf Assembly with Temperature Control, Shelf System With Temperature Control.

The last two are the same component with different normalization. That's a bug.

### Rotary tablet press (11)

Die Set (Compression Die Plate), Feeding System, Feeding System (Hopper and Powder Feed Mechanism), Frame And Base Structure, Frame and Base Structure, Gap Adjustment Mechanism, Powder Discharge System, Rotary Turret, Structural Enclosure and Chassis, Turret (Rotating Compression Station), Turret (Tooling Station Assembly).

This one has the most normalization bugs. "Frame And Base Structure" vs "Frame and Base Structure" is a case variant. Three separate Turret entries that should be one. Feeding System appears twice. 5 of the 11 "false positives" are really just 2 components with bad normalization.

### Single-use bioreactor (7)

Aeration System, Air Removal System, Frame and Base Structure, Sampling and Addition Ports, Sensors and Instrumentation, Structural Enclosure and Chassis, Temperature Control System (heater/chiller).

### Smartphone (5)

Lithium-ion Battery Module, Printed Circuit Board (PCB) Assembly, Radio Communication Module, Structural Enclosure and Chassis, User Interface Module (Display and Keypad/Touchscreen).

## Normalization problems

### Duplicates in the output

Some of these "false positives" are just the same component normalized two different ways. "Frame And Base Structure" vs "Frame and Base Structure" is a case bug. "Shelf Assembly with Temperature Control" vs "Shelf System With Temperature Control" is a semantic duplicate. These inflate the FP count artificially and need to be fixed in the normalization pipeline.

### Pipeline recall of the gold standard is terrible

| Technology | Pipeline recall |
|---|---|
| Pharmaceutical Lyophilizer | 0.429 |
| Rotary tablet press | 0.200 |
| Single-use bioreactor | 0.300 |
| Smartphone | 0.000 |

This measures exact canonical name matches between pipeline output and gold standard. Smartphone is 0.000, which looks alarming until you realize it's entirely a naming problem:

- Gold standard says "Battery", pipeline says "Lithium-ion Battery Module"
- Gold standard says "Vacuum System", pipeline says "Vacuum System" (this one matches)
- Gold standard says "Display Module", pipeline says "User Interface Module (Display and Keypad/Touchscreen)"

The pipeline finds the same concepts. It just names them differently because the gold standard was normalized via a fresh LLM call (not in the technology-scoped vocab), while pipeline components went through the standard run. This is the main thing to fix next.

## Takeaways

The judge is fine. No false negatives, no real false positives once you account for the gold standard being incomplete.

The actual problem is normalization. The pipeline and gold standard independently pick different canonical names for the same concepts, and the normalizer sometimes produces case variants or semantic duplicates of the same component. That's what needs fixing next.

  --goldstandard data/goldstndrd.csv \
  --configs v1v1v1 d3v1v1 \
  --judge-model openai:gpt-4.1 \
